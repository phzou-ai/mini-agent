## Executive Summary

The normal local A2A task path is coherent:

```text
message/send
  -> MainAgentCore
     -> route decision
        -> local message
        -> local task
           -> queued/running
           -> input-required or completed/failed/canceled
           -> artifact and event projection
```

`MainAgentCore` is now the main local A2A lifecycle entry point. The remaining
risks are concentrated in asynchronous execution, restart behavior, direct
message failure presentation, remote proxy ordering, and the temporary
coexistence of the legacy service runtime.

## Findings

### P0. Durable A2A Message Idempotency

**Resolved, 2026-08-01.** Schema migration 10 adds a durable ingress/outcome
record keyed by `messageId`. `MainAgentCore` reserves it before routing and
persists the route reference plus its message, Task, delegation, or structured
failure outcome.

A duplicate now returns that resolved outcome, the persisted failure, or a
retryable `message_in_progress` error. It cannot route, invoke a model, create
a Task, delegate, or call a tool again. SQLite uniqueness is the cross-process
correctness boundary; the in-memory lock remains only an optimization.

Regression coverage includes a store restart replay, two separate SQLite
connections racing on an in-progress Message, persisted provider failure, and
the v9-to-v10 migration.

Relevant code:

- `vermay/main_agent/core.py`, `_prepare_message_route()`
- `vermay/main_agent/store.py`, `reserve_message_ingress()`

### P1. Historical: asynchronous task input was not frozen

**Resolved, 2026-08-01.** Schema version 11 gives each Context Message a stable
sequence and stores a local Task's input sequence when the Task is created.
The worker receives only `taskId` and derives its bounded initial history from
that persisted cut. A later independent Message therefore cannot become the
Task's initial input; `runtimeThreadId` remains reserved for explicit task
continuation. See [Durable Context Input Cut](../../components/backend/runtime/context-input-cut.md).

The remaining limitation is intentionally narrower: this is a causal history
cut, not a complete prompt snapshot. Dynamic system policy, model selection,
skills, memory, MCP data, and tool availability are not frozen by M6.

### P1. Historical: queued, running, and cancellation-pending tasks had no startup reconciliation

**Resolved, 2026-08-01.** The in-process `ThreadPoolExecutor`, active-task
set, and notifier still do not survive a restart, but schema version 12 now
persists an unclaimed worker command alongside every queued local execution
slice. `MainAgentCore.reconcile_startup()` resubmits only a valid remaining
command, transitions `running` and `cancel_requested` tasks to an explicit
retryable failure, and retains blocked Tasks with their pending continuation.

This is a single-host liveness improvement, not a distributed scheduler. The
focused semantics and tests are documented in
[Startup Reconciliation](../../components/backend/runtime/startup-reconciliation.md).

### P1. Historical: approval and ordinary user input were collapsed too early

**Resolved for the local process path, 2026-08-01.** The local runner maps an
`approval_required` interrupt to `auth_required` and a
`user_input_required` interrupt to `input_required`. `MainAgentCore` validates
the matching public continuation operation against the durable pending
continuation record before it accepts and queues a command.

M2 now also validates every locally owned process transition and pairs it with
its lifecycle event atomically. The remaining related risk is restart recovery
after a continuation has been accepted and queued.

### P2. Local message failures are not persisted

Task execution errors are persisted as failed task state and events. Direct message execution has no equivalent failure record. If `local_message_responder.respond()` or its stream fails, the API can return an error while the context contains only the user message.

After a reload, the user may see an unanswered message even though the request failed.

Relevant code:

- `vermay/main_agent/core.py`, `_handle_local_message()`
- `vermay/main_agent/core.py`, `_stream_local_message()`

Recommended direction:

- persist a structured agent error message or message outcome;
- use the shared `{code, message, retryable}` error contract;
- keep the persisted error separate from a successful assistant answer.

### P2. A2A and legacy service runtime resources are still duplicated

**Implementation update, 2026-08-02:** resolved for executor ownership. The
default `MainAgentCore` now receives an application-owned executor; the legacy
service keeps its compatibility executor and no longer supplies work resources
to the normal A2A path. See
[Runtime Composition And Remote Proxy](../../components/backend/runtime/runtime-composition-and-remote-proxy.md).

`create_app()` creates an `AgentService`, which eagerly builds a runtime, and then creates another runtime for `MainAgentCore`. Both use the default SQLite/checkpoint paths. The new core also borrows the legacy service's task executor.

The current behavior passes tests, but runtime ownership and shutdown responsibility remain split. It also creates duplicate model/tool/checkpoint resources in one process.

Relevant code:

- `vermay/api/app.py`, service and core construction
- `vermay/api/service.py`, eager runtime and executor ownership

Recommended direction:

- let the A2A application own one task executor and one main runtime stack;
- keep the legacy service isolated as a temporary management compatibility layer;
- remove the dependency from `MainAgentCore` to the legacy service executor before deleting the old API.

### P2. Remote proxy state can regress on stale snapshots

**Implementation update, 2026-08-02:** resolved. Snapshot refresh and cancel
forwarding now live in `MainAgentCore`, which rejects backward and
terminal-conflicting remote updates. See
[Runtime Composition And Remote Proxy](../../components/backend/runtime/runtime-composition-and-remote-proxy.md).

Remote task snapshots are applied directly to the local proxy task. There is no monotonic transition or remote version check. An older `running` snapshot arriving after a `completed` snapshot could regress the local proxy status.

Relevant code:

- `vermay/api/a2a/adapter.py`, `_apply_remote_task_snapshot()`
- `vermay/main_agent/store.py`, `update_task_status()`

Recommended direction:

- do not transition a local proxy away from a terminal state;
- compare remote event/version/timestamp metadata when available;
- centralize transition validation instead of relying on route-specific checks.

### P2. A local task can be created without an execution runner

`MainAgentCore` intentionally supports message-only test cores, but an explicit local task route with no `local_task_runner` creates a task that remains `created` with no worker scheduled. The current test suite codifies this behavior.

This is acceptable for isolated fixtures but unsafe as a production configuration. The application boundary should either reject this configuration or persist a clear failed capability result.

## Confirmed Correct Behavior

- `MainAgentCore` owns the normal local A2A lifecycle.
- `taskId` is the durable A2A task/process identity.
- `runtimeThreadId` is the LangGraph checkpoint continuation identity.
- Normal local task events form a coherent `created -> queued -> running -> input-required/completed/failed/canceled` path.
- `task_artifact_created` describes output availability. An A2A artifact update may have no task-level `status`; this is not itself a lifecycle error.
- Remote tasks retain separate local proxy and remote task identities.

## Historical Follow-up Architecture Re-check

The following follow-up originally reviewed the in-progress P0 safety work. Its findings remain useful historical context; the continuation handoff described below was completed on 2026-08-01.

### Validation Snapshot

```text
Continuation/store/A2A focused tests: 117 passed
Full suite: 484 passed
```

The stale A2A approval fixture now provides `input_request.kind=approval_required`. Compatibility tests also construct an isolated no-op legacy runtime rather than mutating the repository's default local database.

### P0. Asynchronous Approval Resume Resolves Its Own Pending Request Too Early

**Resolved, 2026-08-01.** The former asynchronous `resume_task()` path recorded `task_resumed`, marked the task queued, and then scheduled a worker that re-read the lifecycle history. That lookup treated `task_resumed` as a resolved request, so the worker could no longer find `approval_required`.

`main_agent_pending_continuations` now owns the blocked control state. The acceptance transaction validates and consumes that record, records `task_resumed`, and queues a frozen approval or user-input command. The worker validates only that accepted command against the current task record; it does not infer pending state from events. Queued approval and ordinary-input regression tests both execute to completion.

The remaining related risk is restart recovery for a command that has been accepted and queued but whose in-process worker never starts.

### P1. Durable Task Input Cut

**Resolved for causal initial input, 2026-08-01.** A local Task now stores the
sequence of its `inputMessageId`, and worker execution queries only Context
Messages at or before that cut. Later independent Messages cannot enter the
initial Task prompt, even if the worker starts later or is reconstructed by a
future recovery path. The queued-worker callback no longer carries a Python
message list.

The remaining M6 scope is route-specific prompt budgeting and treatment of
memory, skills, MCP content, tool output, and summaries. It is not a task
input-causality gap.

### P1. Interruption Kind Must Drive Process State and Continuation Operation

**Resolved for the local process path, 2026-08-01.** The local runner maps an `approval_required` interrupt to `auth_required` and a `user_input_required` interrupt to `input_required`. `MainAgentCore` validates the corresponding public continuation interface and retains the structured pending request separately from lifecycle events.

M2 now provides the single validated transition policy for every owned-process
state mutation. Startup reconciliation is also implemented; any later remote
continuation support remains separate work.

### P2. Lifecycle and Runtime Ownership Remain Split

**Implementation update, 2026-08-02:** resolved for the normal A2A path. This
section remains as the review-time evidence that led to the implemented
composition and remote-proxy contract.

`MainAgentCore` is the normal local A2A lifecycle owner, but `create_app()` still creates a legacy `AgentService` runtime and lends its executor to the core. The A2A adapter synchronizes remote proxy status through a separate path, while local owned-process transitions use the validated store policy.

**Required design correction:** after the P0/P1 process-correctness work, compose one executor and main runtime stack at the application root. Keep adapter responsibilities limited to protocol translation and retain a separate monotonic policy for remote proxy synchronization.

### Historical Recommended Order

1. Persist direct-message failure presentation.
2. Consolidate runtime/executor ownership and harden remote proxy synchronization.
3. Return to the remaining token-budgeted context-assembly scope after local process correctness is clear.
